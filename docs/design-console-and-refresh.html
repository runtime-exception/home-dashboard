01现状的三个结构性问题

三项需求都不是"加个页面"能解决的，下面三个约束如果不动，功能就落不了地。

1.1 config.json 是产物，不是配置源

config.json 由 nginx/generate-config.sh 在容器启动时从 conf.yml 生成。如果控制台只写 config.json，下一次 docker compose restart 就会被启动脚本覆盖回旧值——用户改的配置直接消失。

必须修正

写入目标改为 conf.yml，保存成功后再由服务重新生成 config.json。这样 conf.yml 保持唯一真源，重启、重装、迁移都不会丢配置。

1.2 conf.yml 目前是只读挂载

docker-compose.yml 里是 ./conf.yml:/etc/docker-tools/conf.yml:ro，容器内进程无法写入。需要改为读写挂载，并把配置目录统一到一个共享卷中，让 NGINX 和 API 服务都能访问。

1.3 当前视觉层级靠装饰堆出来

现有界面上，同一屏里同时出现了网格底纹、两个角落发光块、菜单栏、页面标题，以及四处全大写加宽字距的英文小标签（PERSONAL INFRASTRUCTURE、WORKSPACE、LOCAL NETWORK）。

这些元素各自都在争夺注意力，但没有一个在传递信息——"LOCAL NETWORK" 对用户判断该点哪个工具毫无帮助。真正需要被区分的"在线 / 离线"状态反而被压缩成右上角一个小圆点。这就是"看着不太方便"的根因：装饰的对比度高于信息的对比度。

Apple 的做法正好相反：背景纯色、装饰归零，把对比度预算全部留给内容本身——字号、字重、留白。

为什么单独开一个容器，而不是塞进 NGINX 容器

  • 职责单一：NGINX 镜像里加 Node 运行时会显著变大，且需要引入进程管理器（s6/supervisor）来同时守护两个进程，失败模式变复杂。
  • 权限最小化：只有 API 容器需要写权限，NGINX 容器可以继续只读挂载 ./data。即便静态站被攻破，也无法写配置文件。
  • 可独立重启：改完配置只需要重启 api，NGINX 无需中断，静态资源不受影响。
  • 与构建链一致：Dockerfile 已经在用 node:22-alpine 构建前端，复用同一个基础镜像，不引入新语言。

附带简化

现在每个工具都会生成一段独立的 NGINX location 块，配置改动就必须重载 NGINX。改造后健康检查可以统一用一个通配 location，把工具 ID 通过变量传给上游，NGINX 配置变成静态的，工具增删不再需要碰 NGINX。这一步能顺带删掉 generate-config.sh 里最脆弱的正则校验逻辑。

03配置写入与备份

一次保存要同时保证三件事：YAML 合法、JSON 与 YAML 一致、旧配置可回滚。

保存流程

  1. 鉴权：校验会话 cookie，未登录直接 401。
  2. 结构校验：按 schema 检查必填字段、ID 格式、URL 格式、标签引用是否存在。不通过则返回 422 与逐字段错误，不写盘。
  3. 备份：把当前 conf.yml 复制到 data/backups/conf-YYYYMMDD-HHmmss.yml，保留最近 20 份，超出的按时间淘汰。
  4. 原子写 YAML：写入临时文件 conf.yml.tmp，fsync 后 rename 覆盖。rename 在同一文件系统内是原子操作，不会出现写一半的半个文件。
  5. 生成 JSON：从内存中的配置对象序列化出 config.json，同样走"临时文件 + rename"。
  6. 返回新配置：响应体直接返回保存后的完整配置，前端无需再发一次 GET。
一致性

第 4 步和第 5 步之间如果进程崩溃，会出现 YAML 已更新而 JSON 是旧值的情况。解决方式是让 API 在每次启动时都无条件重新生成一次 config.json——这样任何不一致都会在下一次启动时自愈。同理，这套机制也让用户手工编辑 conf.yml 后重启容器即可生效。

并发与文件属主

  • 并发写：API 是单进程，内部用串行队列处理写请求即可，不需要文件锁。同时只允许一个保存操作在途。
  • 文件属主：容器内以 root 写入会让宿主机上的 conf.yml 变成 root:root，之后用普通账号编辑会失败。建议 compose 里给 api 服务指定 user: "${UID:-1000}:${GID:-1000}"，并在文档里说明。
  • 配置漂移：用户绕过控制台直接改 conf.yml 时，API 无法感知。可以在启动时记录文件哈希，或在读取时比对 mtime，检测到外部修改就重新加载。控制台上给出"配置文件已被外部修改"的提示。

04配置模型 v2 与标签

标签采用"顶层注册表 + 工具内引用"的两级结构，而不是在工具上直接写标签字符串。

为什么用注册表而不是裸字符串

诉求裸字符串注册表（推荐）
统一改名要改 N 个工具改一处即全局生效
标签配色无法承载每个标签带 color
筛选栏顺序不可控数组顺序即显示顺序
校验引用完整性无法校验可检测孤儿引用
删除标签残留字符串可级联清理

兼容与容错

  • version 缺失或为 1 时按 v1 解析，tags 视为空数组，工具上的标签忽略。
  • 工具引用了未注册的标签：加载时保留但标记为未知，控制台里以警告色提示，避免整个配置因一个笔误打不开。
  • 删除标签时：若仍有工具引用，API 默认拒绝并返回引用列表（409）；请求可带 ?force=true 强制级联移除。
  • 前端在无标签时隐藏整个筛选栏，不出现空的分段控件。

05接口契约

所有管理接口统一挂在 /api/admin 下，由 NGINX 反代到 api 容器。除登录接口外全部要求有效会话。

认证

方法路径说明
POST/api/admin/session登录。请求体 { username, token }，成功返回 200 并下发 Set-Cookie；失败 401
GET/api/admin/session查询当前会话，返回 { authenticated, username }
DELETE/api/admin/session登出，清空 cookie 并作废服务端会话

配置

方法路径说明
GET/api/admin/config读取完整配置（含 tags），供控制台表单初始化
PUT/api/admin/config全量替换，走完整的校验与备份流程
POST/api/admin/config/validate只校验不写盘，返回 { ok, errors[] }，用于表单实时提示
GET/api/admin/config/export下载 conf.yml 原文
POST/api/admin/config/import上传 YAML 覆盖现有配置，导入前强制校验

工具与标签

方法路径说明
POST/api/admin/tools新增工具
PUT/api/admin/tools/:id修改工具，id 不可变更
DELETE/api/admin/tools/:id删除工具
PATCH/api/admin/tools/reorder拖拽排序，请求体 { ids: [...] }，数组顺序即展示顺序
POST/api/admin/tags新增标签
PUT/api/admin/tags/:id修改标签，id 不可变更
DELETE/api/admin/tags/:id删除标签，被引用时返回 409 与引用列表

备份

方法路径说明
GET/api/admin/backups列出备份文件名、大小、时间
POST/api/admin/backups/:name/restore回滚到指定备份，回滚前先备份当前配置

错误响应格式

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "配置校验未通过",
    "details": [
      { "field": "tools[2].internalUrl", "message": "必须是 http 或 https 地址" },
      { "field": "tools[5].tags[0]",    "message": "标签 docs-x 未在 tags 中注册" }
    ]
  }
}

控制台把 details[].field 直接映射到对应输入框下方的红字提示，用户不需要自己去猜哪一行出错。

校验规则

字段规则
tools[].id必填，^[a-z0-9][a-z0-9-]*$，全局唯一，长度 2–40
tools[].title必填，1–60 字符
tools[].description可选，最长 200 字符
tools[].internalUrl必填，合法 http(s) URL
tools[].publicUrl可选，留空表示无公网地址
tools[].accent可选，#RRGGBB 格式
tools[].tags字符串数组，每项必须存在于顶层 tags 中
tags[].id同工具 ID 规则，全局唯一
tags[].label必填，1–12 字符（筛选栏是横排的，过长会挤压）
tags[].color可选，#RRGGBB 格式，缺省时由 ID 哈希生成
networkTest.*protocol 限 http / https；port 为 1–65535；timeoutMs 为 500–30000

06认证与安全

这是整个改造中风险最高的部分——它把一个纯静态站点变成了有写权限的服务。

凭据来源

# docker-compose.yml
services:
  api:
    environment:
      ADMIN_USERNAME: ${ADMIN_USERNAME:?必须设置}
      ADMIN_TOKEN: ${ADMIN_TOKEN:?必须设置}
      SESSION_TTL_HOURS: "8"

沿用现有 .env / .env.example 的用法，账号密码不进代码库。:? 语法让变量缺失时 compose 直接报错退出，避免出现空凭据的裸奔实例。

启动时校验

  • 任一环境变量缺失或为空 → 拒绝启动，日志打印明确的修复指引。
  • ADMIN_TOKEN 长度小于 8 字符 → 拒绝启动。宁可让用户改一次配置，也不要接受 123456。
  • 下限最初定为 16，2026-09-15 放宽到 8。8 只是兜底，不构成强度保证，仍建议用 openssl rand -base64 24 生成。
  • 启动日志里只输出令牌长度与指纹前缀，不输出原文。

会话机制

  • 登录：比对用户名与令牌，令牌用 crypto.timingSafeEqual 做定长比较，防止通过响应时间推断字符。比对前先各自 SHA-256，规避长度不等导致 timingSafeEqual 抛错。
  • 会话令牌：登录成功后生成 32 字节随机数作为会话 ID，存于服务端内存 Map，附带过期时间。客户端只拿到不透明的随机串，不携带任何用户信息。
  • Cookie 属性：HttpOnly（JS 不可读，防 XSS 窃取）、SameSite=Strict（防 CSRF）、Path=/、Max-Age 与 TTL 一致；当门户走 HTTPS 时追加 Secure。
  • 过期：默认 8 小时，每次有效请求滑动续期。会话存内存意味着 api 重启后需重新登录——对个人工具来说这是可接受的取舍，换来的是不必引入存储。

防暴力破解

同一来源 IP 连续 5 次登录失败后锁定 15 分钟，返回 429 与剩余等待秒数。计数器放内存即可，重启清零可以接受。登录接口额外加 300ms 固定延迟，把离线爆破的成本抬高一个量级。

其他

  • 写操作审计：每次保存记录时间、来源 IP、变更摘要到日志，便于事后排查"谁把配置改了"。
  • 限流：管理接口整体限流（每 IP 每分钟 60 次），防止误写的脚本打爆服务。
  • 不暴露端口：api 容器不映射宿主机端口，只通过 compose 内网被 NGINX 访问。
  • HTTPS 建议：控制台提交的是长期令牌，明文 HTTP 传输等于裸奔。部署时应通过 Lucky 之类的反向代理加 TLS，或在可信内网内使用。
务必知晓

改造后，门户的访问权限等于服务器的配置写权限。请把 :8080 的暴露范围限制在可信网络内，不要直接映射到公网。

07Apple 风格视觉规范

核心不是"用苹果的颜色"，而是套用它的决策顺序：先删装饰，再用留白和字重建立层级，最后才谈色彩。

7.1 五条原则

  1. 装饰归零。 删掉网格底纹与角落发光块。背景用一个接近纯白的灰，让内容和背景之间的边界由卡片承担，而不是由花纹承担。
  2. 层级只靠三样东西。 字号、字重、留白。全大写加字距的英文小标签全部删除——它们是装饰，不是层级。
  3. 一个强调色。 全局只有 Apple 蓝 #0071e3 作为可交互色（按钮、链接、选中态）。工具各自的 accent 降级为图标底色和标签色，不再影响卡片边框。
  4. 圆角连续、阴影极轻。 统一圆角半径，阴影只在悬浮时出现，且要用两层叠加（近距离细阴影 + 远距离柔阴影）而不是一层黑雾。
  5. 动效克制。 只做 opacity 与 transform，时长 200–300ms，缓动曲线 cubic-bezier(.4,0,.2,1)。不做位移超过 8px 的动画。

7.2 字体阶梯

字体栈优先系统字体，Apple 设备上自动落到 SF Pro，Windows 落到微软雅黑，不需要外链字体。

10风险与取舍

项风险应对
安全面扩大 门户从只读变成可写，凭据泄露等于服务器配置被改 强制令牌强度、限速锁定、api 不映射端口、建议 TLS 接入、限定 :8080 暴露范围
文件属主变更 容器内以 root 写 conf.yml，宿主机上变成 root 所有，普通账号无法编辑 compose 指定 user: "${UID}:${GID}"，并在 README 中说明
YAML 与 JSON 不一致 写入过程中崩溃会留下不一致状态 原子写入 + 每次启动无条件重新生成，任何不一致在下次启动自愈
配置漂移 用户绕过控制台直接改 conf.yml，控制台显示的可能是旧值 按 mtime 或哈希检测外部修改并提示
多标签页不同步 控制台保存后，已打开的首页标签页仍是旧配置 为 /api/config.json 加 ETag，首页在窗口重新获得焦点时校验一次
标签删除破坏引用 工具引用了已删除的标签，筛选失效 默认拒绝删除并返回引用列表，需显式 force 才级联清理
健康检查路由改造 从"每工具一段 location"改为通配反代，需要重新验证所有工具仍能被正确探测 改造后逐个验证 15 个工具的状态判定，特别是返回 401/404 的情况
视觉重构影响既有截图 README 与仓库首页截图全部失效 安排在最后阶段，重构完成后统一替换

需要你确认的取舍

  • 会话存内存：api 重启后需重新登录，换取不引入额外存储。若希望重启后仍保持登录，需改为 HMAC 签名的无状态 Cookie 或落盘会话。
  • 控制台用抽屉而非弹窗：抽屉能保留左侧列表上下文，代价是小屏幕上体验一般。若主要在手机上看，建议改成全屏页面。
  • 标签数量：label 限制 12 字是为了分段控件横排不挤压。如果标签会更多或更长，筛选栏需要考虑改成可换行的胶囊布局。
  • 是否保留 conf.yml 手工编辑能力：方案完整保留了这条路径（改完重启即可）。如果希望强制走控制台，可以加文件哈希校验并在检测到外部修改时拒绝启动。
